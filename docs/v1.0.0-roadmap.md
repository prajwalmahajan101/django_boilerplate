# v1.0.0 Roadmap

Goal: cut a stable, forkable `1.0.0` of `django_boilerplate` with the
same quality bar that `fastapi_boilerplate` shipped on 2026-06-11
(see its `CHANGELOG.md` § `[1.0.0]`). This document is the
phase-by-phase plan to get there.

**Baseline (as of 2026-06-15, branch `main`).**

- 180 tests pass; pytest coverage **64.03%** with no `--cov-fail-under`
  gate. 13 modules sit at 0–44% (s3, data, filters, valkey,
  permissions, healthcheck, etc.).
- CI runs ruff + `manage.py check` + `makemigrations --check` + a
  single `make test` step. Postgres service container only — no
  Redis/Valkey, no pre-commit step, no `pip-audit`, no SBOM.
- ADRs: 0000 (template), 0001 (fire-and-forget dispatch),
  0002 (exception-HTTP registry). The resilience-kit migration
  (PR #8) is undocumented as an ADR.
- `CHANGELOG.md` has `[Unreleased]` only; no `[1.0.0]` section.
- `LICENSE` present (Apache-2.0). Known-issues backlog in
  `docs/known-issues.md` is cleared (P1–P4 merged).

## Success criteria

A tag `v1.0.0` is cuttable when **all** of the following hold:

1. `pytest` passes with `--cov-fail-under=85` (overall) and
   per-package floors in CI: `apps/core/` 90%, `apps/core/api_log/`
   95%, `apps/api/` / services / repositories 80%. Dormant modules
   are either tested or explicitly listed under
   `[tool.coverage.run] omit`.
2. CI runs unit / integration / e2e against real Postgres + Valkey
   service containers, plus pre-commit, `pip-audit`, and SBOM.
3. The resilience-kit migration is recorded as an ADR; the dormant
   code policy (if adopted) is recorded as an ADR.
4. `CHANGELOG.md` has a complete `## [1.0.0] — YYYY-MM-DD` section
   following Keep a Changelog conventions.
5. AST gates equivalent to FastAPI's `check_dead_utils.py` /
   `check_stale_refs.py` / `test_no_dormant_imports.py` run in CI.
6. README and `docs/INDEX.md` reflect the final shape; no stale
   references to `apps/core/resilience/`, `apps/core/utils/http_client/`,
   etc.

## Phase plan

Phases are sized to ship as independent PRs. Each phase ends with
green CI and a CHANGELOG entry under `[Unreleased]`. The 1.0 cut
itself (M5) only rewrites the heading.

### M1 — CI hardening (smallest, ship first)

Goal: stop merging blind. Make CI catch what local pre-commit
catches today, plus what the FastAPI CI catches.

- Add a **Valkey service container** to `.github/workflows/test.yml`
  alongside the existing Postgres service.
- Add a **pre-commit step**: `pre-commit run --all-files`.
- Add a **`pip-audit` step** keyed on `requirements/*.txt`. Block on
  high/critical; informational on lower.
- Add a **SBOM step** (`make sbom` already exists).
- Split `make test` into three CI steps: `unit`, `integration`,
  `e2e`, so a flaky e2e doesn't blur a unit regression.

Exit: PR green on a fresh fork-clone, no new policy yet.

### M2 — Coverage gate + tests for low-coverage modules

Goal: lift coverage from 64% to ≥85% honestly, then gate it.

- Triage the 13 low-coverage modules into **(a) on the request path**
  vs **(b) dormant**. Per-module decisions:
  - `apps/core/permissions.py`, `apps/core/healthcheck/`,
    `apps/core/filters/`, `apps/core/data/` → request-path, need
    tests.
  - `apps/core/utils/s3.py`, `apps/core/cache/valkey*` (if not used
    by `@resilient`) → candidates for dormant policy.
- Write integration tests for the request-path set. Match the
  FastAPI scope: handler edges, middleware ordering, DRF throttle
  buckets, healthcheck probes, RBAC 403 path, error-envelope
  contract, audit-log dispatch under burst.
- Once coverage is ≥85% with the dormant set `omit`-ed, add:

  ```ini
  # pytest.ini
  addopts = --cov-fail-under=85
  ```

  and per-package floors as a follow-up CI step
  (`coverage report --include='apps/core/*' --fail-under=90`, etc.).

Exit: `pytest` fails locally if coverage dips. CI enforces the same.

### M3 — Policy & AST gates

Goal: encode the rules so drift is caught at PR time, not review.

> **Scope reduced after M1+M2.** Five of the six AST gates originally
> scoped here already shipped:
> - `check_dead_utils.py`, `check_layering.py`,
>   `check_thread_safety.py`, `check_openapi_metadata.py`,
>   `check_stale_refs.py` — all five live in `.pre-commit-config.yaml`
>   today and M1 wired pre-commit into CI, so they block PRs.
> - M2 added the *docstring* half of the dormant-module policy
>   (`Dormant:` callouts on 9 modules + `.coveragerc omit`).
>
> M3's remaining net-new is therefore narrow:

- **Dormant-import AST gate.** Mirror FastAPI's
  `test_no_dormant_imports.py`: walk every `.py` under `apps/` (and
  `config/`) with `ast`, fail the build if any `Import` /
  `ImportFrom` node targets a module currently in the dormant set
  (source of truth: `.coveragerc omit` plus the `Dormant:` docstring
  marker). The gate has one escape hatch — a same-PR integration
  test that exercises the imported symbol, surfaced via a
  `# allow-dormant-import: <reason>` line comment that the gate's
  AST walker honours.
- **Dormant set documentation.** Add a `## Dormant modules` section
  to `docs/INDEX.md` listing the nine modules + the activation
  procedure for each (which docstring/comment to remove, which
  setting flips them live, which test file to add).
- **ADR-0004 — Dormant-module policy** (if the M3 PR's review
  surfaces a non-obvious dormant-vs-request-path call worth pinning
  for future contributors).

Exit: an in-tree `from core.utils.s3 import ...` (with no escape
comment) fails the build. The dormant set stays small and discoverable
in INDEX.md.

Exit: stale doc references and dead utils block the PR.

### M4 — ADRs + docs sweep

Goal: capture the decisions a forker needs to understand the shape
of the codebase.

- **ADR-0003 — outsource resilience to `resilience-kit`.** Mirror
  FastAPI's ADR-0003. Context: M7+M8 (PR #8) migrated
  circuit-breaker / retry / throttle / SSRF / Fernet to the kit.
  Decision: in-tree bridges only (`RequestIdBridgeMiddleware`, kit
  error handler). Consequences: re-exports keep import paths
  stable; kit owns the resilience surface going forward.
- **ADR-0004 — dormant module policy** (if M3 adopts it).
- Walk `docs/INDEX.md`, README, `docs/architecture.md`,
  `docs/resilience.md`, `docs/configuration.md`. Remove every
  reference to deleted paths. Replace with kit imports.
- Verify the dependency graph in `docs/dependency-management.md`
  matches current `requirements/*.in`.

Exit: `check_stale_refs.py` passes; a new reader can land in the
repo and trust the docs.

### M5 — Release cut

Goal: tag `v1.0.0`.

- Move every `[Unreleased]` entry under
  `## [1.0.0] — <date>` in `CHANGELOG.md`. Group by Migrated /
  Added / Changed / Fixed / Performance / Refactored, matching
  FastAPI's structure.
- Add a "Coverage note" if any package floor is still red, with the
  ratchet plan.
- Bump version in `pyproject.toml` (or wherever the version lives).
- Tag: `git tag -a v1.0.0 -m "v1.0.0"` then push the tag.
- Optional: GitHub Release with the CHANGELOG section as the body.

Exit: `git tag -l` shows `v1.0.0`. README badge (if any) updated.

## Out of scope for 1.0

These are deferred to 1.x to keep the cut focused:

- Docker-based CI test execution (P3 from `known-issues.md`).
- OpenTelemetry trace export (the metrics shim stays as-is).
- A `next-django-boilerplate` equivalent of FastAPI's `next-forge`
  story.
- Multi-tenant scaffolding.

## Sequencing rationale

M1 first because it's the cheapest and most reversible — no
production code touched, immediate signal lift. M2 is the largest
phase and should be split into multiple PRs (one per module group).
M3 depends on M2's dormant triage. M4 can run in parallel with M2
once the dormant set is known. M5 is the cleanup that closes the
release.

Aggressive estimate: M1 in one sitting, M2 across a week, M3+M4 in
parallel over a few days, M5 in an afternoon. Conservative: double
that.
