[`resilience-kit==0.1.0rc1`](https://pypi.org/project/resilience-kit/0.1.0rc1/)

## Deviations from `docs/MIGRATION-from-boilerplate-embedded.md`

Five kit-side gaps surfaced during the migration; all logged in
[`docs/m7-kit-integration-notes.md`](./docs/m7-kit-integration-notes.md)
and feed the kit integration report (see follow-ups):

1. **No `DjangoSettingsSource`** — kit's `ResilienceConfig.ready()` only
   reads `RESILIENCE["services"]`. The `RESILIENCE` dict's other keys
   are documentation, not config. Env vars (`RESILIENCE_*`) remain the
   only override surface.
2. **No `resilience_kit.utils` sub-package** — MIGRATION promised
   `utils.{log_sanitization,network,timing,function_logger,data}`
   re-exports. None exist. Kept locally; not deleted.
3. **No `GlobalThrottle`** — kit ships only `IP/UserTier/Burst/Endpoint/Auth`.
   Dropped `GlobalThrottle` from `DEFAULT_THROTTLE_CLASSES`.
4. **`core.metrics` surface incompatible** — kit's Protocol-based
   `MetricsSink` is not a drop-in for the boilerplate's free-function
   shim + bounded-label contract. Kept `core.metrics`.
5. **Exception bridge required** — kit's `ExternalServiceError` etc.
   inherit `ResilienceKitError`, not `BaseCustomError`. Bridge
   (`class BaseCustomError(ResilienceKitError)`) keeps every domain
   subclass envelope-aware. Composition wrapper in `handler.py` makes
   `EXCEPTION_HANDLER` work without breaking the envelope contract.

# M8 — Upgrade to resilience-kit v0.1.0 (folded into this PR)

The kit's [v0.1.0 release](https://github.com/prajwalmahajan101/resilience-kit/releases/tag/v0.1.0)
ships four additive helpers that close the M7 dogfooding blockers
flagged in the integration report. Rather than stack a separate PR
on top of an unmerged rc1 branch, the upgrade is folded here as six
more commits — the diff against `main` is identical either way and
the rc1 → 0.1.0 audit trail stays clean.

## End-to-end proof (smoke test)

Anonymous `GET /api/accounts/me/` (expected 401):

```
HTTP/1.1 401 Unauthorized
X-Request-Id: 1e43827d5faa4fcfa3551acfcf9caa27
X-Correlation-Id: 1e43827d5faa4fcfa3551acfcf9caa27
…

{"success":false,
 "message":"Authentication credentials were not provided.",
 "data":null,
 "errors":[{"code":"NOT_AUTHENTICATED",
            "message":"Authentication credentials were not provided.",
            "field":null,"details":null}],
 "request_id":"1e43827d5faa4fcfa3551acfcf9caa27"}
```

`request_id` matches `X-Request-Id` header. **rc1 would have returned
`"request_id": null`** — that's the dogfooding blocker the bridge
closes, verified end-to-end against `runserver`.
